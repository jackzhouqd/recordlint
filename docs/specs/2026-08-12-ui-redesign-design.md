# 界面重设计与训练模块 — 设计说明

日期：2026-08-12
范围：`qaudit` 本地审核服务的界面、易用性、以及新增的印章模型训练与上线能力。
不在范围：规则引擎判定逻辑、OCR、切分、CLI 判定口径（均不改动）。

---

## 一、动机

现状三个问题：

1. **界面**：`server.py` 内联一段 30 行 CSS，白底表格，8 个平铺导航项，观感与「质量记录预审系统」的定位不匹配。
2. **易用性**：复核是卡片流 + 每卡一张小图，翻页丢上下文，判定只能鼠标点，没有批量操作。而实测数据里存在 622 页/463 页量级的**系统性问题**，逐条点击是纯粹的浪费。
3. **功能**：`tools/` 下已有完整的印章数据集与训练链路（crop / synth / pages / merge / train），但只能命令行运行，界面里完全没有；训练出的模型也没有任何途径接入判定。

## 二、决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 视觉方向 | 深色为默认，浅色可切换（cookie 记忆） | 深色出科技感；浅色供打印与投影 |
| 前端依赖 | 允许本地打包：htmx 2.0.4 + Chart.js 4.4.7 | 无构建链路、无 Node、全离线；仅两个静态文件随包分发 |
| 渲染范式 | 保留服务端渲染，htmx 做局部刷新 | 不引入 SPA 复杂度，交互体验接近 SPA |
| 训练深度 | 训练工作台 + 模型上线 | 模型只输出状态标签，判定阈值仍在 `rules.yaml` |
| 交付节奏 | 一次做完，分七阶段 | 避免中途风格打架 |

**被否决的方案**：只重写 CSS（做不出三栏工作台与实时训练日志）；Vue/React SPA（需 Node 构建链路，与私有化交付和经费约束冲突）。

    model.py        训练工作台
  static/
    app.css         设计系统

`server.py` 保留为垫片是硬要求——现有 `tests/test_server_auth.py`、`tests/test_web_ops.py` 依赖
`from qaudit.server import Handler` 与 `srv.Config`，203 项测试必须保持全绿。

### URL 兼容

`/run/<run_id>` 必须继续直接渲染复核页并返回 200（测试断言页面正文含「只读账号」），
不能改成 302 跳转。新路径 `/review?run=<id>` 作为别名。

## 四、设计系统

CSS 变量定义在 `:root`，`[data-theme="light"]` 覆盖。默认深色。

- 底 `#0b0f14` → 面板 `#111823` → 悬浮 `#17202c`；描边 `#24303f`
- 主色青 `#2dd4bf`；级别色 CRITICAL `#ff5f56` / HIGH `#ff9f43` / MEDIUM `#e3b341` / LOW `#7d8da1`
- 全部数字 `tabular-nums`；规则号、指纹、坐标、路径用等宽字体
- 面板 1px 描边 + 四角刻线（HUD 观感），不堆阴影、不用大圆角
- **证据图容器强制浅色底 `--paper`**：扫描件是白纸，深色底会让红框与印章失真；图像本身不加任何滤镜

严谨性落在界面上的硬约束：

1. 每条疑点必显示 `规则号 + 条款原文 + 置信度 + 像素坐标`
2. 批次页固定展示**指纹卡**：规则版本 / 规则指纹 / 引擎版本 / OCR 模型 / 模型版本
3. 判定必署名，界面显示「由谁在何时判定」
4. 模型页显式标注「按源印章分组切分，共 N 组」，防止合成样本跨集导致准确率高估

## 五、信息架构

顶栏：品牌 → 主导航（总览 / 复核 / 档案 / 规则 / 模型 / 系统）→ 当前批次选择器 → 主题切换 → 用户。

| 页面 | 内容 |
|---|---|
| 总览 | KPI（页/单据/疑点/待复核/判真率）、级别分布环形、规则命中 Top10、档案疑点密度、复核进度、运行中任务实时进度、「继续复核」直达未判定的 CRITICAL/HIGH |
| 复核工作台 | 左：筛选 + 紧凑疑点列表；中：大幅证据图（缩放平移、整页↔局部）；右：规则说明 + 条款 + 置信度 + 判定 + 备注 + 历史。键盘 `↑↓`/`J K` 切换、`1 2 3` 判定、`Enter` 存并下一条、`F` 全屏、`?` 帮助。多选后可「同规则同档案批量判假」。保留卡片流作为浏览模式 |
| 档案 | 档案 → 单据 → 页 树，含该档案历次批次对比 |
| 规则 | 按 A/B/F/U 分组、搜索、命中数排序、行内改级别、变更历史抽屉 |
| 模型 | 样本库 / 标注 / 合成 / 训练 / 模型版本（详见第六节） |
| 系统 | 发起审核与任务、用户管理、操作日志、金标准与评测 |

## 六、模型训练与上线

### 数据表（幂等 `CREATE TABLE IF NOT EXISTS` + `ALTER TABLE` 迁移）

```sql
seal_sample(sample_id PK, path, source_doc, source_page, source_key,
            synthetic INT, synth_kind, created_at)
seal_label (sample_id PK, label, labeler, labeled_at, note)
model      (model_id PK, kind, version, path, trained_at, trainer,
            samples INT, groups INT, accuracy REAL, metrics TEXT,
            status TEXT)          -- draft / active / retired
```

`run` 表已有 `model_versions` 列，训练模块上线后写入实际模型版本。

### 关键设计

- **标注进度存库不存浏览器**：可多人分工、可追溯到人、可审计。现有 `tools/annotate.html` 的 localStorage 方案保留作为离线备用。
- **训练是后台任务**：复用 `jobs.py` 的线程 + `task` 表模式，页面用 htmx 轮询拉实时日志。
- **评估按源印章分组切分**，界面显式展示组数——同一枚真章派生的退化样本不得跨越训练/验证边界。
- **上线机制**：`rules.yaml` 新增两条印章状态规则，各配 `reject_labels`、`min_confidence`。
  模型只回答「这枚章是什么状态」，判不判违规仍由规则决定，保住可解释性。
  未上线模型时规则自动跳过，不报错。

  规则编号取自**客户侧已有的规则清单表格**：`B12_seal_clarity`（清晰完整）与
  `B13_seal_upside_down`（倒盖）。实施中发现最初拟用的 `B11` 在客户表格里并不存在
  （`需求澄清项` 页「B09～B11 共 7 条」是原表笔误，实际只有 6 条），已一并修正。
  两条拆开而不合并成一条，是因为交付节奏本就不同：B13 倒盖的合成即真实（旋转 180°），
  不依赖人工标注就能训到可用（客户表格标为「二期第一批」）；B12 清晰度必须有真实标注
  才能验收（「二期第二批」）。合并会迫使质量部要么全开要么全关。
- 批次指纹加入 `model_version`，历史结论仍可重放验证。

## 七之二、report.html

独立报告是命令行审核的产出，也是对客传阅件，因此有两条硬约束与服务端不同：

1. **自包含**——证据图内联为 base64，样式表由 `app.css` **读入内联**而不是 `<link>` 引用，
   打开时不发起任何外部请求。样式表被挪走会让报告变成一片素文本，因此有专门的回归测试。
2. **可打印**——`@media print` 强制白底并避免卡片跨页断裂。主题选择存 localStorage
   （报告没有服务端，用不了 cookie）。

判定仍存浏览器本地并导出 JSON 供 `qaudit gold` 合入金标准集，
`data-key / data-doc / data-page / data-rule / data-level` 是导出契约，测试锁死。
键位与服务端复核工作台统一（`J`/`K` 移动、`1`/`2`/`3` 判定），避免两处习惯打架。

## 九、风险

| 风险 | 处置 |
|---|---|
| 现有 `qaudit.db`（2.3MB，含已有批次）被迁移破坏 | 迁移全部幂等，只新增表与列，不改既有列 |
| 训练样本量不足导致模型不可用 | 界面显式展示每类样本数与组数，样本不足时禁止上线 |
| 深色主题下扫描件证据图对比度失真 | 证据图容器强制浅色底，图像零滤镜 |
| 前端依赖引入影响软件审批 | 两个文件随包分发、可审计、无网络请求；README 显式说明 |
