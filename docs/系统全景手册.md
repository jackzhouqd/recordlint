## 一、这套系统在解决什么问题

### 1.1 业务场景

制造业的外购件/外协件入厂时随带一套质量记录：检验证明单、检验记录、工序流转卡、
审查报告单、供方合格证等，多为纸质件扫描成的 PDF/TIF/JPG。质量部要按本单位的填写规范
逐页做**形式性审核**——日期写没写满 8 位、范围值用没用「～」、空栏有没有划「/」、
印章清不清晰正不正、多页记录填没填页码、复制件盖没盖确认章。

典型规模：一批几十份档案 = 上千页。一个归档包动辄一两百页，里面混着几十份
独立单据。人工逐页翻，翻到后面必然眼花。

### 1.2 这个系统做什么

把上千页压成**上百条可读疑点条目**，每条带：

- 原图红框定位（能一眼看到问题在纸的哪个位置）
- 规则依据（国标条款或通行惯例，规则包可覆盖）
- 置信度（告诉你这条有多可信）
- 规则号（能追到具体是哪条逻辑判的，也能一键停用）

人从「翻上千页找问题」变成「看上百条已定位的疑点，逐条判真假」。

### 1.3 这个系统**不**做什么——这是设计基石，不是免责声明

> **本系统不作最终判定结论。**

这句话不是写来推卸责任的，它决定了整套系统的技术取舍：

| 如果定位是「自动判定通过」 | 实际定位是「人工预审助手」 |
|---|---|
| 必须追求高准确率，宁可漏报不误报 | **召回优先**，宁可误报不漏报——漏检是风险，误报只是多看一眼 |
| 每条结论必须可靠到能签字 | 结论只需可靠到「值得人看一眼」，置信度 0.4 的提示也有价值 |
| 手写 OCR 识别不准 = 系统不可用 | 手写识别不准 → 加像素兜底，宁可多报 |
| 模型必须做到极高准确率才能上线 | 模型只回答「这枚章是什么状态」，判不判违规由规则决定 |

最终判定由使用方质量职能按其程序签署，这是制度决定的，不是技术能改变的。
把系统定位钉死在「预审助手」，反而让每个技术决策都有了明确的方向。

**如果客户预期是「系统判定合格即可通过」，这套方案的定位、验收标准与责任划分全部要重谈。**
这个认知差必须在第一次沟通就当面澄清。

### 1.4 三条硬边界

1. **C 类规则本期不实现**——凡需要与工艺规程、ERP/LIMS/QMS 比对的判定
   （实测值是否超差、设计图版次是否与工艺一致、批次号与配套单是否对得上），
   本页信息不足以判定。这类是「实质性错误」，质量价值最高，但依赖外部数据。
2. **视觉判定只作提示**——划改识别是启发式（长而细的横线穿过文字中部），
   置信度按 0.4 输出；圆形印章的倾角无意义，直接跳过不判。
3. **「不得缺项」与现场执行存在张力**——「备注」整列空白按 字面属违规，
   实测 251 页，但现场普遍如此。系统做成可配置 + 整列合并一条，**最终口径由质量部拍板**。

### 1.5 系统的真正价值在哪

不在「自动发现问题」，而在这三件事：

1. **把系统性问题暴露出来**。实测最大的四类问题——缺设计图版次 610 页、
   复印确认章措辞不符 445 页、复印章位置不对 380 页、备注栏整列空白 251 页——
   人工抽检根本发现不了这种「全批都错」的模式，因为每一份单独看都不显眼。
2. **让口径变成可讨论的对象**。规则写在 `rules.yaml` 里，级别、阈值、适用表单
   都能改。质量部说「备注栏空白我们不算违规」，改一个白名单当场生效。
   以前这种口径分歧只能靠开会传达，现在能落成配置、能留痕、能回溯。
3. **积累金标准集**。人工每判一条真/假，都在给系统攒验收依据。判到 300～500 页，
   双方封存，验收就有了唯一裁判，不用扯皮。

## 二、全局架构与数据流

### 2.1 四层定位——全系统最重要的概念

```
档案（doc）          一个归档包，通常是一个 PDF 或一个目录
  └─ 单据（unit）    一份独立表单，可能横跨多页，也可能页码不连续
       └─ 页（page） 一页扫描件
            └─ bbox 页内像素坐标 (x, y, w, h)
```

**单据这一级是后加的，加它之前有一整类规则无从判起。**
一个 180 页的 PDF 里其实是几十份独立单据，按整包判「页码是否连续」毫无意义。
切出单据后，「声明共 4 页实际只有 3 页」「多页记录未填页码」才有了正确的判定单元。

每条疑点最终都锚定到 `(doc_id, page_no, bbox)`，这是证据图能按需裁剪的前提。

**界面上的下钻链路**（四层定位的落地）：

```
档案页 /archive          列出全部档案，含页数/单据数/疑点数/条/页/各级别分布
  └─ 点档案 → /archive?doc=X          该档案的单据表 + 页表 + 历次审核对比
       └─ 点单据号 → /archive?unit=Y  单据信息卡 + 该单据的页 + 该单据的疑点
            └─ 点「复核」 → /review?sel=<finding_key>   直接跳到复核台并选中该条
                 └─ 中栏证据图上的红框即 bbox
```

单据视图会在「声明总页 ≠ 实际页数」时直接标红告警——这是缺页的直接证据。

> **单据的页集合允许不连续**，因此 `unit` 表存的是实际页号数组而不是首末页号区间。
> 交错装订时（p13 是 3102A 的第 1 页、p14 是 3103A、p15 又回到 3102A），
> 按区间取会把邻居单据的页算进来，进而算出假的缺页。

## 三、识别层（把扫描件变成结构化事实）

### 3.1 接入 `ingest.py`

**统一长边 2200 像素**（约 A4@190dpi）。为什么必须归一化：后续所有像素阈值——
印章最小面积 `page_area * 0.00025`、划改线长度 18～35% 页宽、单元格最小 25×15——
都是相对页面尺寸的比例。TIF 是 300dpi、JPG 是 200dpi，不归一化这些阈值就没法统一。

**只引用不复制**。系统全程只记录原始文件路径 + 页号，从不复制图片。
证据图在需要时用 `load_page_image(source, page_no)` 重新渲染再裁剪。
理由：受控载体不能翻倍——复制一份就是多一份需要管控的受控介质。

**两个实测踩过的坑**：

- `cv2.imread` 不支持中文路径，档案名全是「低涡转子平衡组件（PN-XXXX)22-02-10-7」
  这种。改用 `np.fromfile` + `cv2.imdecode`，TIFF 再回退到 PIL。
- `cv2.imwrite` 遇非 ASCII 路径**静默返回 False**，曾导致 4396 枚印章样本里
  3187 枚没写进磁盘而清单照常生成。现在写盘一律走 `imwrite_jpg`（编码后 `write_bytes`），
  且裁图任务结束时会自检「清单与磁盘一一对应」。

### 3.2 OCR `ocr.py`

RapidOCR（onnxruntime，PP-OCRv4 模型随包约 15MB），**完全离线，不联网**。

**页级缓存是这套系统能迭代的关键**。缓存 key 是页面像素的抽样哈希：

```python
h.update(str(image.shape).encode())
h.update(image[::7, ::7].tobytes())   # 每 7 行 7 列抽一个像素，足以唯一标识一页
```

效果：首次全量 1453 页约 **2.2 小时**（5.4s/页）；改规则重跑全量 **2 分钟**（0.09s/页）。
规则调优的迭代成本因此几乎为零——这是整个项目能在短时间内把误报从 3349 条压到
2248 条的前提。

> **缓存是敏感数据**。`.ocr_cache/` 里是档案全文，敏感度高于图片本身
> （图片要人看，全文可全文检索）。18MB / 1453 个 JSON。对外发送任何产物前必须清掉，
> 部署时也要和客户明确它的存放与清理要求（需求澄清清单第 30 项）。

### 3.3 版面分析 `layout.py`

**为什么用自适应阈值而非 Otsu**：档案里大量是复印件，底色重且不均匀，
全局阈值会把整片底色当成前景。用 `ADAPTIVE_THRESH_MEAN_C`（块 25、常数 15）。

**表格线提取**：横向核 `(w//30, 1)`、纵向核 `(1, h//40)` 做腐蚀+膨胀，
分别留下横线和竖线，或运算得到表格骨架。

**「线掩膜中的洞即单元格」**：对表格骨架取轮廓，`RETR_CCOMP` 模式下
层级为「有父轮廓」的就是封闭空洞。过滤掉过小（<page_area×0.0004 或 <25×15 像素）
和过大（>page_area×0.25）的。这个办法比检测线交点鲁棒得多，因为扫描件的线经常断。

**短横线段 = 划改候选**：用 `(12,1)` 核提取横向连通域，保留高度 ≤5 像素、
长度在 18 到 35% 页宽之间的。比字宽长、比表格线短的横线，大概率是划改线。
这仍然是启发式，印刷下划线和分数线会误报，所以置信度只给 0.4。

**列定位 `column_x_range`**：定位「检验员」「实际」这类表头列的 x 区间。两个要点：

- 同一页可能有多处同名文字（表头「检验员」和上方栏目标签「检验员」），
  **取最靠下的一处**——数据行在表头之下，取错整列判定全落空。
- 列宽优先用表格单元格边界，比按文字宽度外扩准确得多。

### 3.4 印章检测 `seal.py`

**红色在 HSV 里跨 0°**，必须取两段：`H∈[0,12]` 和 `H∈[166,180]`，`S≥60, V≥60`。

**闭运算核必须「横宽纵窄」——这是一个踩坑换来的设计**：

```python
cv2.getStructuringElement(cv2.MORPH_ELLIPSE, (13, 5))   # 宽 13，高 5
```

质量证明单的检验章是**逐行纵向密排**的。用各向同性的大核（比如 9×9）会把整列印章
粘成一条竖长条，连通域面积超过 `page_area*0.12` 的上限后被整体丢弃，
结果判成「整列无章」——B07 检验员栏缺章的误报从 190 条降到 30 条，
这是三个根因里最主要的一个。

**`Seal` 的两个语义属性**：

- `is_frame`：`fill_ratio < 0.18`。红色矩形**线框**（「此件与原件一致」的外框）
  填充率低，不是实体印章。做印章数量判定时必须排除。
- `angle_reliable`：`rectangularity >= 0.80`。圆形章的最小外接矩形角度是随机的，
  没有意义。B01 印章歪斜只对方形/多边形章判定，圆章直接跳过——**宁可漏报不误报**。

**印章重叠的判据不是 IoU**：换核后印章碎片相邻会被 IoU 判成重叠。
改成「较小一枚被覆盖比例 ≥50%」（`overlap_ratio`），误报从 55 条降到 14 条。

**圈内碎片在检测端并回**（`merge_nested`）：印色偏淡时闭运算连不通圈内笔画，
一枚圆章会碎成「外圈 + 圈内文字」多个连通域，圈内碎片被外圈外接框 100% 包含，
恰好落在上面「覆盖比例」判据的枪口上（220-164 第 2 页实测误报）。`detect()`
返回前把被其他实体章外接框包含 ≥90% 的组件并入所属印章；红线框不吸收内部
组件，避免合并后填充率上升被误判为实体章。

### 3.5 表单类型识别 `formtype.py`

**这是误报抑制里投入产出比最高的一环**。管理要求 本身就是按表单分别规定的，
而且供方随带的「产品质量证明书/合格证」是**外单位自制文件**，格式由供方自定，
强行套用公司内部表单的填写格式要求会产生系统性误报。

三级匹配，顺序即优先级：

1. **标题区匹配**（页面上 1/3）——最可信
2. **全页匹配**——标题被裁掉或 OCR 漏读时
3. **表头结构兜底**——部分表单标题只写零组件名（「XX 组合件」），
   但栏目组合固定。例如同时出现「规定 + 实际 + 检验员」三栏即认定为质量证明单类。

分成两个集合：

- `internal`（由规则包给出）：`is_internal()` 的口径；规则的实际适用范围仍由各自的 `applies_to` / `exclude_forms` 决定
- `supplier`（供方合格证、产品合格证）：多数格式规则通过 `exclude_forms` 排除

实测约 7% 页面仍为「未识别」——上线前应与使用方确认是否有遗漏的表单类型。

### 3.6 倾斜校正 `deskew.py`——为什么默认关闭

功能已实现且有测试，但默认关闭，理由是实测数据：

| 指标 | 实测值 |
|---|---|
| 倾角中位数 | 0.20° |
| 90 分位 | 0.75° |
| 超过 1° | 7% |
| 超过 2° | 2% |

而开启会让 OCR 缓存**整体失效**（图像变了，哈希就变了），全量重识别约 2.2 小时。
收益远小于代价。客户实际扫描件若歪斜明显，`audit --deskew` 一键开启即可。

> **整页方向识别（90°/180° 旋转）仍未做**，本批样本中未出现。

## 四、规则引擎

### 4.1 核心设计：规则库与代码解耦

`config/rules.yaml` 是**质量部可以直接维护的基线**：

```yaml
A01_date_format:
  enabled: true
  level: HIGH
  title: 日期未写满 8 位或分隔符不规范
  clause: 产品质量记录的日期按“2023.06.01”的格式写满 8 位
  params:
    exclude_forms: ["供方合格证", "产品合格证"]
```

代码只认 `rule_id`，级别、阈值、适用表单、白名单全部来自 YAML。
质量部提出的调整**不用改代码，当场生效**。这是整个方案对客承诺里最实的一条。

界面上的调整**不回写 YAML**，而是记为 `rule_override` 覆盖项，带变更人、时间、理由，
可在操作日志追溯，也能一键还原回基线。这样既保住带条款注释的版本基线，又留了痕。

### 4.2 规则门控

```python
@staticmethod
def applies(spec, form_type) -> bool:
    if form_type in spec.params.get("exclude_forms", []): return False
    if include := spec.params.get("applies_to"): return form_type in include
    return True
```

`applies_to` 是白名单（F 类强绑定表单类型），`exclude_forms` 是黑名单
（A/B 类通用规则排除供方文件）。故障修理通知单的规则不会作用到质量证明单上。

### 4.3 四类规则的划分依据

划分标准是**判定所需信息的来源**，不是难度：

| 类 | 判定依据 | 条数 | 特点 |
|---|---|---|---|
| **A 文本确定性** | OCR 文本 | 18 | 纯函数，可单元测试，最可靠 |
| **B 视觉判定** | 像素与几何 | 12 | 仅作提示，置信度普遍偏低 |
| **F 表单专项** | 各表单要求 | 12 | 强绑定表单类型 |
| **U 单据级** | 需先完成单据切分 | 4 | 判定单元是单据不是页 |
| **C 需外部真值** | 工艺规程/ERP/LIMS | 0 | **本期不实现** |

默认启用 44 条（`A05` 计量单位 mm 省略、`B09` 页码须在页脚中间 两条默认关闭，
等质量部确认口径）。

### 4.4 注册表 + 异常隔离

每个规则模块用装饰器注册：

```python
@rule("A01_date_format")
def check_date(ctx: PageContext, spec: RuleSpec) -> list[Finding]:
    ...
```

`run()` 逐条执行，**单条规则抛异常不会拖垮整页**——捕获后产出一条
`level=LOW, confidence=0.0` 的「规则执行异常」疑点。审核 1453 页跑到一半崩掉
是不可接受的，少一条判定可以接受。

`Finding` 是 `frozen=True` 的数据类，规则只产生新对象，不修改既有结果。

### 4.5 误报抑制的五层设计

真实档案（复印件、手写、浅色扫描）上，天真实现会产生海量误报。
首轮全量跑出 **3349 条**（2.3 条/页），其中 **77% 是规则写法问题而非档案问题**。
五层压制：

**第 1 层：表单类型门控**（见 3.5）

**第 2 层：语境约束**

- 范围值规则必须**带计量单位**才判定，否则批次号 `22-02-10-7`、
  合同号 `2021-407-602A-1636` 全被误伤
- 小数位数规则先判断该数字是否属于零件号（`PN-2832B` 里的 `.15` 不是小数）

**第 3 层：像素兜底**

手写内容常被 OCR 漏识。凡涉及「是否为空」的判定，一律追加**墨迹率检测**与
**印章覆盖检测**——OCR 读不出不等于那里是空的。同列连续空白合并成一条疑点，不刷屏。

**第 4 层：档案级折叠**

同一档案内某规则命中 ≥5 页且覆盖率 ≥60% 时，HTML 报告折叠成一条：
「本档案 24/24 页均缺设计图版次」。

**第 5 层：批次级折叠**

一条规则在整批里散命中超过 30 页时合成一条批次级疑点，附各档案分布。

> **关键：`findings.json` 始终保留逐页完整清单**，折叠只影响给人看的 HTML。
> 否则按页评测会被破坏——金标准集是按 `(doc_id, page_no, rule_id)` 三元组计分的。

### 4.6 全量基线复盘：四个噪声源

首轮 3349 条里，逐条核对原图定位出四个根因：

| 噪声源 | 条数变化 | 根因 | 处置 |
|---|---|---|---|
| A09 页码 | 675 → 8 | 厂内预印表单是「共X页第Y页」，与要求示例顺序相反但信息完整 | 两种顺序都判合规，加 `strict_order` 供收紧 |
| A15 单位缺失 | 429 → 28 | 页级判定：页面提到「流量」就要求整列实测值带单位 | 改为**行级**，只查关键词同行 |
| B07 检验员缺章 | 190 → 30 | ①纵向密排印章被闭运算粘成超大连通域后整体丢弃 ②「检验员」是表头栏位时章盖在标签右侧 ③复印件上原章是黑色 | 闭运算核改 13×5；列与同行两处都查；复印件豁免 |
| B02 印章重叠 | 55 → 14 | 换核后碎片相邻被 IoU 判成重叠 | 判据改为「较小一枚被覆盖比例 ≥50%」 |

**这张表的价值在于它说明了一件事：绝大多数「误报」不是算法能力问题，
而是规则写法与现场实际不匹配。** 解决办法是拿真实样本逐条核对原图，
不是换更强的模型。

修复后剩余 2248 条，其中 1686 页次集中在四类**真实的系统性合规问题**：

| 问题 | 页数 | 说明 |
|---|---|---|
| 缺「设计图版次」 | 610 | 758 页质量证明单里 80% 全页无此信息，已核对 OCR 全文确认非识别遗漏 |
| 复印确认章措辞 | 445 | 写作「复印件与原件一致」，要求为「此件与原件一致」 |
| 复印确认章位置 | 380 | 盖在左下角，要求右下角空白处 |
| 「备注」栏整列空白 | 251 | 按 字面属违规，现场普遍如此，**口径待质量部拍板** |

其余 460 页次为零散真问题：多页单据未填页码 66、日期格式 59、页码不连续 58、
小数位超限 43、检验员栏缺章 30、范围值用短横 28、单位缺失 28 等。

### 4.7 单据切分 `segment.py`

**输入是 `PageDigest`（页面摘要），刻意不含图像**——一个归档包上百页，
缓存整图会吃掉几个 GB。摘要含：表单类型、关键字段、页码标记、是否有标题、
文本长度、**内容指纹**。

**页码标记解析**覆盖三种写法：

- `第1页共4页`、`共4页第1页`（厂内预印表单，顺序相反）
- `13/19页`（供方证明单，常见形式 `1/1份-13/19页`）
- 页码被 OCR 拆成两行时，退而在整页文本里找

**切分信号，按优先级**：

1. **关键字段取值变化**——最硬的证据。换了零件号/批次号就是换了单据。
   优先级高于页码顺延，因为供方文件的连续页码会跨越多份零件证明单。
2. **页码标记**：声明为第 1 页即新单据；顺延页号则继续当前单据
3. **当前单据已按声明页数收满**
4. **表单类型变化**（「未识别」不作依据，避免把续页切碎）
5. **出现表单标题**且当前单据已有内容

**两个非平凡的处理**：

- **`declared_total` 只在单据首页页码为 1 时才可信**。供方证明单的「13/19页」是
  他们整套文件的连续编号，里面本就含多个零件的证明单，据此判缺页会大批误报。
- **交错装订合并**。实测档案里同一份供方证明单的多页会被其他零件的证明单隔开
  （p13 是 3102A 的第 1 页，p14 是 3103A，p15 又回到 3102A）。连续切分会把它切碎，
  产生「声明 3 页实际 1 页」的假缺页。因此按关键字段签名合并——
  **单据的页集合允许不连续**。

**内容指纹**只取文本不取像素：同一份记录的两次扫描像素必然不同，但文字一致。
用于 U04 判定「同一批产品把同一份记录重复传递」（）。

## 六、存储、可追溯与权限

### 6.1 为什么是 SQLite

单机部署 + 服务化架构：跑在质量部一台机器上，科室内多人用浏览器访问同一份数据。
表结构按服务端形态设计，**将来换 PostgreSQL 只改 `store.py` 一层**。
用标准库 `sqlite3` 而非 PostgreSQL，是因为离线安装介质与运维成本最低。

### 6.2 五项指纹 = 可复现

受监管制造场景的硬要求是**任何一条历史结论都能重放验证**。每个批次登记：

| 指纹 | 含义 |
|---|---|
| `rules_version` | 规则库版本号 |
| `rules_hash` | 规则库文件 SHA256 前 16 位 |
| `engine_version` | 引擎版本 |
| `ocr_model` | OCR 模型标识 |
| `model_versions` | 已上线的判定模型版本（JSON） |

**同一页 + 同一规则版本 + 同一模型版本 → 必然得到同样的结论。**
这五项常驻在总览页的「版本指纹」卡上，不需要翻数据库。

### 6.3 审计与权限

- **所有写操作进 `audit_log`，追加写不修改**：谁在何时导入了什么、判了什么、
  改了哪条规则、标注了哪枚章、上线了哪个模型。
- **判定人一律取自登录会话，不接受前端传入**。前端即便伪造 `reviewer` 字段也无效。
  这是「判定必须追溯到人」的硬要求，批量判定也不例外（逐条写日志）。

### 6.3.1 任务状态的收敛

任务状态活在数据库，执行线程活在进程。**进程被杀 / 机器重启 / 服务重启后，
DB 里的 `running` 永远不会有人来改**——界面上会挂着一个永远转圈的任务，
并且「已有任务在运行」的互斥会一直挡住新任务。

两条出口：

1. **服务启动时自动收敛**：`Store.reconcile_tasks()` 把所有 `running` 标为
   「服务重启，任务已中断」。启动日志里会打印收敛了几个。
2. **界面手动标记取消**：任务表里运行中的行有「标记取消」按钮。
   **只改状态不强杀线程**——后台线程没有安全的中断点，强杀可能让样本库写到一半。
   真在跑的任务会继续跑完并覆盖这个状态；卡死的任务则就此从界面上消失。

> 中断的任务**进度不保存**，需要重新发起。裁图入库是幂等的（同一枚章重复裁不会
> 产生重复样本），重跑无副作用；审核任务的 OCR 缓存也还在，重跑很快。
- 口令用 **scrypt 加盐散列**存储，绝不明文落盘；命令行不接受 `--password`，
  改用不回显输入，避免落进 shell 历史。
- 连续 5 次口令错误锁定 15 分钟；会话 8 小时过期；
  **停用账号或重置口令立即让既有会话失效**。

三种角色：

| 角色 | 权限 |
|---|---|
| `admin` 管理员 | 用户管理 + 规则维护 + 模型训练 + 导入批次 + 复核判定 + **档案来源维护 / 自由路径** |
| `reviewer` 复核员 | 发起审核 + 复核判定 + 样本标注 |
| `viewer` 查阅员 | 只读，界面不显示判定按钮 |

> **系统没有默认账号**——首次使用必须在服务器上用命令行建管理员，
> 界面无法自助注册。

### 6.4 服务端无 HTTPS

离线单机场景按明文 HTTP 部署，默认只监听 `127.0.0.1`。
供科室多人访问需 `--host 0.0.0.0` 并按网络安全要求做访问控制。
如需加密须由前置反向代理承担（需求澄清清单第 28 项）。

## 七、Web 系统与使用手册

### 7.1 技术形态

服务端只用标准库 `http.server` + `sqlite3`，**不引入任何新的 Python 运行时依赖**。
前端有两个静态文件随包分发：`htmx 2.0.4`（51KB，局部刷新）与
`Chart.js 4.4.7`（206KB，图表）。都是本地文件、无构建链路、**运行期不发起外部请求**，
可随包做软件审批。其余 CSS/JS 全部自研。

界面默认深色（工控台观感），右上角可切浅色供打印投影，选择记在 cookie。
**证据图容器在深色主题下强制浅色底、图像零滤镜**——扫描件是白纸，
深色底会让红框与印章的观感失真。

### 7.2 首次配置

```bash
pip install -r requirements.txt
```

```bash
python -m qaudit.cli user add admin1 --role admin --name 王主任 --db qaudit.db
```

```bash
python -m qaudit.cli serve --db qaudit.db --port 8000 --archive-root "../质量记录档案"
```

浏览器打开 `http://127.0.0.1:8000`。

**档案来源（挂载点）。** 档案不一定和系统放在一起：可能在网络盘、移动硬盘、
另一个盘符，来源还会随年度批次增加。所以「允许审核哪些根目录」是一份可热改的
配置 `config/archives.yaml`，由界面 **系统 → 档案来源** 维护，
**增删即时生效、不需要重启服务**，每次变更写审计日志（`mount_change`）。
没有这份配置时退回 `--archive-root` 的单根模式，老部署不受影响。

新增来源时**在页面上点选目录**，不必手敲路径：页面内嵌一个**服务端目录选择器**，
从盘符开始逐层进入，点「选此目录」即回填路径并自动带出名称。
之所以是「服务端」选择器而不是系统的文件夹对话框：浏览器出于安全**不会**把本机
绝对路径交给网页（`webkitdirectory` 只给相对路径），而挂载点要的正是服务器上的
绝对路径——只能由服务端列目录、管理员点选。选择器**仅列目录、不列文件、不读内容**，
且锁死在管理员：其能力边界与「管理员本来就能手填任意路径」完全一致。
UNC 共享（`\\nas\share`）无法枚举，输入框保留手填。

发起审核页是一个**逐层下钻的浏览器**：来源 → 子目录 → 子目录，任意一层都能直接
提交审核，因此 `质量记录档案/20/batch-0001` 这种深层档案能精确选到，
不必整包全审。**浏览器只传相对路径 `来源名/子路径`，服务端解析后校验归属**，
越界（`..`、绝对路径注入、符号链接指到外面）一律拒绝——这是 Web 侧的路径安全边界。

**自由路径**是逃生通道：以 `--allow-custom-path` 启动后，管理员可在界面直接填本机
绝对路径发起审核，**默认关闭**，且每次都写审计日志（`audit_custom_path`）。
常规做法仍是把来源登记进「档案来源」，那样才有可追溯的名字。

命令行 `audit` 不受此限制——它跑在操作员自己的机器上，边界就是操作系统权限。

### 7.3 六个入口

| 入口 | 干什么 |
|---|---|
| **总览** | 开机第一眼。KPI（页/单据/疑点/待复核/判真率）、级别分布环形图、规则命中 Top10、档案疑点密度、复核进度、运行中任务实时进度、版本指纹卡。一个「继续复核」按钮直达未判定的 CRITICAL/HIGH |
| **复核** | 主战场，三栏工作台，见 7.4 |
| **档案** | 档案 → 单据 → 页 的层级视图，含每份档案的疑点密度与历次审核对比 |
| **规则** | 按 A/B/F/U 分组、即时搜索、启停、调级别、填变更理由、一键还原基线 |
| **模型** | 印章状态分类器：样本库 / 标注 / 合成与训练 / 模型版本，见第八章 |
| **系统** | 发起审核与任务、金标准与评测、全部批次、操作日志、**档案来源**、用户管理 |

### 7.4 复核工作台——怎么高效判完一批

三栏：**左**筛选 + 疑点列表；**中**大幅证据图（滚轮缩放、按住拖动平移、
双击复位、整页↔局部切换）；**右**规则说明 + 条款 + 置信度 + 判定 + 备注 + 历史。

证据图 100% = **整图适应窗口**，缩放与平移一律走 CSS `transform`，
不依赖容器滚动条。早期版本用 `scrollLeft/scrollTop` 平移，1 倍时容器
`overflow:hidden` 而图高于容器，底部内容既滚不到也拖不动——等于看不全。
配套约束写在 `app.css`：`.evidence` 的行列必须是 `minmax(0,1fr)`，
否则 auto 轨道会被内容撑到原图高度，图片的 `max-height:100%` 就失效。

#### 推荐的复核顺序（实战建议）

1. **先看总览的「规则命中 Top10」**，找出命中特别集中的规则。
   实测里 F02（缺设计图版次）610 页、A13（复印章措辞）445 页——
   这些几乎肯定是系统性问题，不是 610 个独立缺陷。
2. **点进那条规则，先判几条确认口径**。看清楚到底是真问题还是规则写歪了。
3. **确认后用批量判定一次判掉**。右栏会显示「本档案该规则共命中 N 条，
   其中 M 条未判定」，一键批量。批量同样绑定登录账号、逐条写审计日志。
4. **剩下的零散疑点用键盘流逐条过**。`J` 下一条、`1/2/3` 判定，手不离键盘。
5. **筛「仅未判定 + CRITICAL/HIGH」收尾**，确保高危的没漏。

> **批量判定是这套系统最大的效率杠杆。** 622 页逐条点击和一次批量判定之间的差距，
> 决定了质量部愿不愿意真的用它。

### 7.5 规则维护

什么时候该动规则：

| 情况 | 动作 |
|---|---|
| 某规则误报率极高，且核对原图确认是规则写歪了 | **改代码**，不是停用规则 |
| 某规则判的是真问题，但质量部认为现场可接受 | **停用**或调低级别，填变更理由 |
| 某规则的口径需要收紧/放宽 | 改 `rules.yaml` 的 `params` |
| 试了不对想退回 | 界面点「还原」，回到规则库基线 |

界面上可改的三样东西：

| 改什么 | 怎么改 |
|---|---|
| 启停、级别 | 规则行上直接选，填变更理由 |
| **参数**（阈值、适用表单、白名单） | 展开规则行下的「参数」，用 YAML 编辑 |
| 全部还原 | 「还原」回规则库基线；「还原参数」只清参数覆盖 |

参数编辑有两条保护：

1. **只存被改动的项，不存全量快照。** 存快照的话，日后规则库基线新增或调整某个
   参数默认值时，这条覆盖会把老值永久钉死，而且没人看得出来。
2. **不接受未知参数。** 只能调整规则已有的参数，新增参数需要改代码——
   否则会出现「界面上写了个参数但代码根本不读」的静默失效。

界面改动记为覆盖项、带人带时间带理由，**下一次审核生效，不改动既有批次的历史结论**。

### 7.6 金标准与评测

**计分口径**：判真的算召回，判假的算误报，**存疑与未判定都不计分**。

为什么这么定：人工往往只判了一页里的部分疑点，把未判定当误报会严重低估准确率。
金标准集就在日常复核中自然长大，不需要专门组织标注。

建议验收指标（召回优先——质量部真正怕的是漏检，误报只是多看一眼）：

| 类别 | 漏检率 | 误报率 |
|---|---|---|
| A 类 | ≤ 2% | ≤ 20% |
| B 类 | ≤ 10% | ≤ 35% |
| C 类 | 不纳入本期 | — |

金标准集由质量部指定 300～500 页逐条人工标注，**双方封存**，作为唯一判据；
规则调优只允许改代码与 `rules.yaml`，**不允许改金标准**。

## 八、印章状态模型

### 8.1 为什么需要模型

要求「印章须清晰、完整、水平正向加盖」。清晰度、缺角、漏墨这类判定，
经典 CV 做不稳定——它们不是「有没有」的问题，是「像不像」的问题。

这是整套系统里**唯一**需要训练的部分。审核主线仍是零训练架构。

### 8.2 数据流水线

```
档案 ──① 裁图入库──▶ 样本库 ──② 人工标注──▶ 合格样本
                                              │
                                    ③ 合成退化 │（倒盖/缺角/模糊/漏墨）
                                              ▼
                                          训练集 ──④ 分组交叉验证训练──▶ npz 权重
                                                                          │
                                                          ⑤ 上线 ──▶ B12/B13 规则生效
```

**① 裁图**：印章已由 `seal.detect()` 定位好，裁图只是按 15% 外扩比例切出来
（留边才看得出缺角），长边统一到 256 像素。红色线框（复印确认章）自动跳过。

**② 标注**：**标注单位是「枚」不是「页」**——不需要画框，只需打标签，
成本比常规目标检测标注低一个数量级。标签集 6 类：
合格 / 缺角 / 模糊 / 漏墨 / 倒盖 / 非印章（最后一类同时是检测器自身的误报反馈）。

> **标注进度存数据库，不存浏览器**。离线标注页的 localStorage 方案只能一个人用、
> 换台机器就丢、也答不出「这条是谁标的」。标注结果最终要进验收材料，必须追溯到人。

**③ 合成**：从人工确认为「合格」的样本派生四类退化——
倒盖 = 旋转 180°、缺角 = 角部置白、模糊 = 高斯模糊、漏墨 = 红色笔画腐蚀 + 噪声。
**这一步是把标注成本从「千页」降到「百枚」的关键**：训练集用「真实清晰章 + 合成退化」，
人工只需标注验证集。

**④ 训练**：手工特征 + sklearn，候选 logreg / RandomForest，
**但导出的永远是线性模型的 npz 权重**（约 41KB），推理十几行 numpy 即可完成。
**部署侧不引入任何新依赖**，形态与现在完全一致。

**⑤ 上线**：模型挂到规则上，批次指纹记录 `model_version`。

### 8.3 特征设计

分四组，是有意为之：

| 特征组 | 维度 | 捕捉什么 |
|---|---|---|
| 红色掩膜下采样 | 32×32 = 1024 | 章面结构与朝向（倒盖） |
| 灰度下采样 | 16×16 = 256 | 笔画浓淡 |
| 拉普拉斯方差 / Canny 边缘率 | 2 | **清晰度**——模糊的关键判据 |
| 连通域碎裂度 | 1 | **断裂程度**——漏墨的判据 |
| 四象限密度 + 长宽比 + 红色占比 | 6 | **缺角**的判据 |

共 1289 维。**清晰度必须用梯度类特征**——红色掩膜本身丢掉了模糊信息，
只看掩膜永远判不出「糊」。

### 8.4 最关键的方法论：按源印章分组切分

合成样本派生自同一枚真实印章。**若随机切分，同源样本会同时进训练集和验证集，
准确率会被严重高估。** 本系统一律用 `StratifiedGroupKFold`，按 `source`（源印章）分组，
并把实际组数写进模型元信息、在界面上显式展示。

这一条如果做错，所有准确率数字都是假的，而且很难被发现。

### 8.5 上线的两道闸

1. **人工标注少于 60 枚禁止上线**。全合成样本上的准确率是**能力上界**，
   不能作为验收依据。「合成」与「几何粗筛」两个自动标注人**不计入**人工标注量，
   否则粗筛出的基底会把计数撑起来，门槛形同虚设。
2. **上线是排他的**。同类模型同时只允许一个 `active`，否则批次指纹会含糊。

### 8.6 判定权仍在规则里

`rules.yaml` 里两条规则，各自配置哪些状态算违规、置信度门槛多少：

```yaml
B12_seal_clarity:      # 印章不清晰或不完整
  reject_labels: ["chipped", "blurred", "faint"]
  min_confidence: 0.75
B13_seal_upside_down:  # 印章倒盖
  reject_labels: ["upside_down"]
  min_confidence: 0.80
```

**模型只回答「这枚章是什么状态」，判不判违规由规则决定。**
验收时要能解释「为什么判它不合格」，不做黑盒。
未上线模型时两条规则自动跳过——少一类判定可以接受，审核报错不可接受。

**为什么拆成两条而不是一条**：交付节奏本就不同。
B13 倒盖的合成即真实（旋转 180° 就是真的倒盖），不依赖人工标注就能训到可用，
客户表格标为「二期第一批」；B12 清晰度必须有真实标注才能验收，属「二期第二批」。
合并成一条会逼着质量部要么全开要么全关。

### 8.7 当前实测状态——**这个模型现在不能用于验收**

链路已完整跑通，冒烟实测：

```
25 页 → 裁出 288 枚印章 → 人工标注 90 枚 → 合成 226 枚退化样本
→ 训练 seal_cls@v1：分组交叉验证 81.6%（源印章 90 组）→ 上线成功
```

**但上线后在真实页面上明显过触发**：8 页命中 31 条，且大量给出「倒盖 100%」
这种不可信的高置信输出。

原因正是 8.4/8.5 反复强调的那条：训练集以合成为主时，交叉验证准确率是能力上界，
真实缺陷的分布与合成退化差得远。要真正可用，需要质量部按每类不少于 100 枚
标注**真实**样本，重训后在人工标注的真实验证集上另行测量。

在此之前建议：`B12` / `B13` 的 `enabled` 保持 `true` 但**不上线任何模型**
（规则自动跳过），或把 `min_confidence` 上调后小范围试用。

### 8.8 操作步骤

界面「模型」页四个页签：

1. **合成与训练 → ① 从档案裁图入库**：选档案、设页数上限，提交后台任务
2. **标注**：`1`–`6` 打标签自动跳下一枚，`←→` 移动，`0` 撤销。默认只显示真实样本
   （合成样本的标签由构造方式决定，不需要人标）
3. **合成与训练 → ② 合成退化样本**：设每类生成概率与随机种子
4. **合成与训练 → ③ 训练**：设交叉验证折数，后台跑，实时看日志
5. **模型版本**：看准确率、逐类精确率/召回率、混淆矩阵热力图，决定是否上线

训练与审核**互斥**——两者都吃满 CPU，同时跑只会互相拖慢。

## 附录 E 术语表

| 术语 | 含义 |
|---|---|
| **档案 / doc** | 一个归档包，通常一个 PDF 或一个目录 |
| **单据 / unit** | 一份独立表单，可能横跨多页、页码可不连续 |
| **疑点 / Finding** | 一条待人工复核的判定结果，锚定到 (档案, 页, 坐标) |
| **规则库 / RuleBook** | `rules.yaml` 加载后的对象，代码只认 `rule_id` |
| **门控 / applies_to** | 规则的适用表单范围，误报抑制第一层 |
| **折叠** | 把系统性问题合并成一条可读条目，只影响 HTML 不影响 JSON |
| **金标准集 / goldset** | 人工判定累积而成的验收唯一判据，双方封存 |
| **版本指纹** | 规则版本+规则指纹+引擎+OCR模型+判定模型，用于结论重放 |
| **分组切分** | 按源印章分组做交叉验证，防止同源样本跨越训练/验证边界 |
| **判真 / 判假 / 存疑** | 人工对一条疑点的三种判定，存疑与未判定都不计分 |
